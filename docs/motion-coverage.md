## Verification contract

`site_motion_browser.cjs` inventories every tracked HTML document against the committed manifest, then checks each of the 71 included routes at 390 and 1440 CSS pixels in motion, reduced-motion and JavaScript-disabled modes: 426 cases. It compares visible text, every link, protected metadata/schema, image source/alt and all heading/paragraph/image/entry/FAQ/footer geometry against the immutable baseline after applying only the approved contact removal to the baseline DOM. Existing overflow is reported separately; no new overflow is accepted. It checks readable headings, motion registration, reduced-motion transitions and keyboard/touch disclosures, and saves screenshots for every included route and width. All form/API and third-party non-font requests are blocked.

The earlier dedicated homepage suite retains 18 cases at 390/768/1440, replay via keyboard/touch, dynamic reduced motion and idle-loop checks. The original service/content suite retains 24 cases including synthetic form errors. All three suites run in the exact-head PR workflow using its existing Playwright installation. No new runtime or test dependency was added. Physical iOS Safari/Firefox and assistive-technology testing are not claimed.

## Motion library assessment (8 October 2026)

Keep the native implementation for this release. `npm view motion version license dist.unpackedSize --json` reports Motion **14.0.0**, **MIT**, package archive unpacked size **750,887 bytes** (not a browser transfer-size estimate). Nothing was installed.

The [official animate documentation](https://motion.dev/docs/animate) lists mini at 2.3 KB and hybrid at 18 KB. Mini animates styles through native APIs; hybrid adds timeline sequences, SVG paths, CSS variables and numeric callbacks. These are the documentation's nominal sizes, not a measured bundle for this site/version.

A concrete future benefit would be a reversible, multi-stage SVG timeline with interruption/resume control. Hybrid `animate(sequence)` could replace the homepage's roughly 20-line timing loop and some custom easing/cancellation bookkeeping; it would not replace the drawing geometry, accessibility policy, scroll measurements or regression tests. `inView` could shorten about 10 lines of the shared observer, without adding a needed capability. Exact net savings require an implementation; no measured code reduction is claimed.

If a later approved effect needs it, pin `motion@14.0.0`, import only the required plain-JS APIs and produce a local static bundle with a separately approved build tool; do not add a floating CDN runtime or React. Risks: extra bundle and build maintenance, changed timing/reduced-motion handling, and rerunning visual regressions. The current shared layer uses CSS transitions and a one-shot IntersectionObserver, so replacing it now adds cost without improving the approved effects.
